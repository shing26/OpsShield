# A1：检测新特征（C/D/P）结果

> 契约：`plans/rca-detection-a1-accept.md`（FROZEN 2026-11-27）
> 分支：`codex/rca-a1-detection`；方法阈值沿用 v2 冻结值
> 数据：RE1-SS dev 75 + RE1-OB dev 75；rep 4–5 与 RE1-TT 均未读取

## 结论（先说结果）

**AC-4 / AC-5 / AC-6 未通过：16 个配置里 0 个合规（合规集为空，无“选中配置”）
→ 按契约 §8，A1 FAIL。** 下表是 best-effort，不是选中配置。

| 最好成绩 | 覆盖 | 误报 | 门槛 |
| --- | ---: | ---: | --- |
| RE1-SS（z0=3.5/k=3/W=60/p=0.6） | 0.840 | 0/75 | 覆盖 ≥0.80 ✅、误报 ≤0.05 ✅ |
| RE1-OB（z0=3.5/k=4/W=60/p=0.6） | **0.493** | **16/75 = 21.3%** | 覆盖 ≥0.80 ❌、误报 ≤0.05 ❌ |

**这是机制层面的失败，不只是“没调够”**：过滤器不能创造新的报警事件。
它在 OB 上只做了两件事（v2 → 过滤，逐 case 对账）：

- “先误报、后真报警”的 case 变成检出：**+12**；
- 原本检出、但首个通过事件被拒的 case 变成 miss：**−11**；
- 净 **+1** 个 case（36→37，0.480→0.493）；v2 没有报警的 case **0 个**被救回。

所以覆盖率并非在数学上被 0.480 锁死（那是我上一版的错误说法，已更正），
而是**兑换预算只有十几个 case**：要到 0.80 需要净 +24，过滤器无论怎么调都没有
这么多可兑换的事件。AC-4 在“只做重排序/重定时”的机制里不可达，但理由是
“没有新增检出”，不是“上限等于基线”。

但实验仍有真结论：**OB 的注入前报警不是“单服务瞬时尖峰”**——过滤只去掉
约 1/3 到 1/2（31 → 14~21），说明它们要么多服务同时异常（C 成立），
要么在时间上持续（D 成立）。v3 附录 A 的“随机尖峰”假设在 OB 上不成立。

## 4. 机制分析（为什么 OB 压不下去）

1. **过滤器不新增事件，只做重选择**：逐 case 对账显示 `none→det = 0`。
   覆盖变化只能来自“FA→后移检出”（+12）与“检出→miss”（−11）的对冲，
   净效应 ±1–2 个 case。这是本次 16 格覆盖都停在 0.44–0.49 的直接原因。
2. **OB 的误报不是尖峰**：若真是单服务瞬时尖峰，C（需 k 个服务同时异常）
   或 D（需持续占比）都会拒掉它们；实际只去掉 10–17 个，剩 14–21 个。
   这些报警在时空上都“长得像故障”。
3. **SS 的误报确实是尖峰**：过滤后误报归零而覆盖只掉 6.7pp，与 v3 附录 A
   的观察一致。两套系统的误报成因不同，单一过滤器无法同时适配。

## 6. 限制与后续

1. **契约设计缺陷**：把“只做重选择的过滤器”和“OB 覆盖 ≥0.80”绑在一起。
   过滤器的兑换预算只有十几个 case（见 §4），补不上 0.48→0.80 的缺口。
   下一份契约必须改机制，而不是改门槛。
2. **下一步需要能“新增检出”的机制**：例如按指标自适应阈值、change-point /
   CUSUM、或按服务历史分位归一；仍只能在 dev 上验证，TT 与 rep 4–5 保持未读。
3. **P 未参与判定**：拓扑相关只记录，避免 A2 迁移时因 TT 无调用图而失效。
   实现只用了 callees（契约写的是 callers/callees，`topology.py` 也只有 callees）；
   P 不进判定，对数字无影响，但属预注册方法的缩小实现，需在签署时知悉。
4. **样本**：每套 75，dev 是 3 reps × 5 services = **每故障 15**（不是 25）；
   覆盖率的 95% CI 约 ±10pp，0.80 门槛本身有抖动。
