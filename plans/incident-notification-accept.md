## 现状与缺口（2026-11-25 实测，基线 `aa05c84`）

已有能力：

- 事故单服务端持久化（ADR-0032），`owner` / `due_at` / `sla_state` 已落库；
- 责任流转 append-only（ADR-0033），`IncidentSlaScanner` 已把 `ok → due_soon → breached`
  做成可审计状态跃迁；
- 评论 @ 已解析出 `mentions` 并写入 `incident_comments`（ADR-0034），但只有**会话内**未读水位；
- 告警到人链路已通（门禁 2，飞书），但那是 **Alertmanager 告警**，不是**事故单事件**。

缺口：

1. **指派后本人不知道**：`transfer` / PATCH owner 只写审计与转交表，被指派人下次刷新列表才知道。
2. **SLA 超时只改状态**：`IncidentSlaScanner` 写 `sla_state` 与审计，不产生任何面向人的提醒。
3. **跨端不可见**：评论未读是 `sessionStorage` 水位，换设备 / 换班即丢。
4. **没有未读汇总**：值班人无法回答"现在有几条与我有关、要我先看哪条"。

## 判定口径

- 「通知」= 一条**持久化、按收件人隔离**的事件记录，不是消息正文的副本。
  通知只带定位信息（事故 ID、标题、优先级、时限、事件类型），**不带 query、诊断正文、评论正文**。
- 「谁收」：
  - `assigned`（含转交）：**新负责人**；操作人本人不收（自己指派给自己不产生通知）。
  - `sla_due_soon` / `sla_breached`：当前负责人 + 创建人；空负责人只发创建人；同一人只发一条。
  - `reopened`：当前负责人 + 创建人；操作人本人不收。
- 「去重」：`dedupe_key` 唯一，冲突**不算错误**（`DuplicateKeyException` 吞掉）。
  - `assigned:<incidentId>:<toOwner>:<minuteBucket>`
  - `sla:<incidentId>:<state>`
  - `reopened:<incidentId>:<minuteBucket>`
  - `minuteBucket = epochSecond / 60`。跨分钟边界的同一事件最多两行，由状态机保证真实事件不重复；
    不接受"为了绝对去重"引入分布式锁。
- 「静默期」：只约束**群机器人推送**，不约束站内记录。默认 `22:00–08:00` 仅 P1 外发；
  其余照常落站内，外发标记 `suppressed=quiet_hours` 并计数——"没发"必须可查，不能静默。
- 「推送」：可选、租户级共享群机器人。`users` 表**没有**邮箱 / IM open_id，
  所以本切片**不做个人 IM 私聊**，也不猜用户身份；要个人私聊先加联系方式字段与用户同意，另开切片。

**不做**：邮件、短信、浏览器 Web Push、个人 IM、评论 @ 的跨端通知、通知内容聚合摘要、
多实例去重、失败重试与退避。

## Acceptance criteria

1. **迁移**：新增 `incident_notifications`：
   `notification_id BIGINT GENERATED BY DEFAULT AS IDENTITY PK / tenant / recipient /
   incident_id / kind / title / priority / due_at / dedupe_key / created_at / read_at`；
   唯一索引 `(tenant, recipient, dedupe_key)`，普通索引 `(tenant, recipient, read_at, created_at)`。
   只新增表，不改 V1–V9；`FlywayMigrationTest` 在空库与已有库上均通过。
2. **原子性**：通知行与事故变更**同一事务**。禁止出现两种半态：
   "事故已改但没人被通知"或"通知已发但事故没改"。事务回滚后该事故**零通知行**（单测证明）。
   唯一键冲突（去重命中）不算失败，事故操作照常成功。
3. **收件人**：按「判定口径」生成；同一事件同一人只一行；`assigned` 不给操作人自己发。
   跨租户用户即使被猜到 `sub` 也不会收到（收件人必须在本租户且启用）。
4. **查询**：`GET /api/v1/copilot/notifications?unreadOnly=&limit=`，只返回**自己**的通知，
   `tenant` 与 `recipient` 只来自 JWT；按 `created_at DESC, notification_id DESC`，
   `limit` 默认 50、上限 100。响应 `{notifications:[...], unread}`，字段
   `{id, incidentId, kind, title, priority, dueAt, createdAt, read}`。
5. **已读**：`POST /api/v1/copilot/notifications/{id}/read` → 204，重复调用仍 204（幂等）；
   非本人 / 跨租户 → 404（不泄漏存在性）。`POST /api/v1/copilot/notifications/read-all`
   → `{updated:n}`。已读时间只写一次，不覆盖。
6. **群机器人（可选）**：`opspilot.incident.notify.webhook-url` 为空即关闭（默认关闭）。
   配置后**事务提交后**异步发送，单次尝试、连接/读取各 3s、不重试、不阻塞请求线程；
   队列有界（默认 256），溢出丢弃并计数，**不得**回落到调用线程。
   `webhook-format=generic|feishu`，默认 `generic`（`{"text":"..."}`）；
   `feishu` 用 `{"msg_type":"text","content":{"text":"..."}}`。
   发送失败只记 WARN + 指标，不影响接口结果，也不回滚事务。
7. **静默期**：`quiet-hours` 默认 `22:00-08:00`（时区 `Asia/Shanghai`，可配），
   非 P1 只落站内、不外发；`suppressed=quiet_hours` 计数可查。P1 不受静默期约束。
8. **前端**：顶栏加通知铃 + 未读角标 + 下拉面板（最近 20 条），点击跳转对应事故并标记已读；
   提供"全部已读"。轮询 30s + 窗口重新聚焦时刷新；不新增 `localStorage` 键，
   不动 `opspilot.incidents.active` 与 `opspilot.comments.seen`；
   窄屏下铃铛不遮挡既有顶栏操作，面板可滚动。
9. **留存**：默认 90 天（`opspilot.incident.notify.retention-days`），每日一次清理，
   单次删除上限 5000 行；清理失败只 WARN，不影响服务。
10. **可观测**：`aiops_incident_notifications_total{kind}`、
    `aiops_incident_notify_webhook_total{result=ok|fail|suppressed|dropped}`；
    审计不新增事件类型（通知是派生数据，事故审计已覆盖事实来源）。
11. **不回归**：事故列表 / 详情 / 评论 / 转交 / SLA 扫描的既有语义与响应字段不变；
    面板契约十层一致，且第 7 层的 `copilot_map` 必须实际包含
    `IncidentNotificationController`，面板侧必须使用字面量路径、不得拼接规避；
    `check_public_copy.py --check` 与 `doc_numbers.py --check` 通过。

1. 浏览器 A 用 `sre-full` 把事故转交给 `sre-limited` → 浏览器 B（`sre-limited`）30s 内出现角标；
2. 重启网关 → B 的未读仍在（持久化，不是内存）；
3. B 点开通知 → 跳到该事故，角标减一；重复点同一条不重复计数；

   直接 `POST` 别人的通知 ID → 404；
5. 配一个本地 HTTP stub 作 webhook：转交一次 → 恰好 1 次 POST；
   stub 超时 5s → 转交接口仍在 1s 内返回，事务已提交，指标记 `fail`；
6. 把系统时间/配置指到静默期，转交 P2 → 站内有记录、webhook 0 次、指标记 `suppressed`；
   转交 P1 → webhook 1 次；
7. 事务回滚演练（可用重复目标触发 409）→ 该事故通知行数为 0。
