# 准入控制与降级作用域：全局 + 租户信号量、429 背压、降级保持全局

状态：已接受（G1 首版已落地 2026-10-22：AdmissionGate + 429/Retry-After + 拒绝/在途指标；按租户降级与全量压测验收仍待 G1 收口）
决定日期：2026-10-22
落地范围：G1（入口准入 + 熔断判据 + 在途/拒绝可观测；G0 只定案，G1 首版改代码）

上下文：2026-10-22 运维审查实测到一条完整的"单人打爆全站"链路：

- 入口**没有任何并发准入**：编排入口只做每用户日配额与计数，随后直接交给虚拟线程池；
  全仓无信号量/限流器，唯一的事实在上限是 Tomcat 的 `maxConnections`。
- 降级状态机是**全局单例**：按"连续 3 次 LLM 失败"开 60 秒 L2，**没有租户/账号维度**；
  而 L1 只是把检索摘成纯 ES，LLM 调用量完全不变——也就是说 L1 并不减少最贵的那份资源。
- 项目自己的压测已经复现：48 并发唯一请求 → 在途峰值 137 → L0→L1；
  0.4 秒内 41 次并发流拒绝 + 76 次 429 → 3 秒内 L1→L2
  （[就绪度台账 2026-09-12 节](../ops/production-readiness-2026-09-12.md)）。
- 配额在并发合并（SingleFlight）折叠**之前**计数，每个被合并的等待者也消耗一次配额。

运维后果不是"变慢"，而是**一个团队写错循环，全公司 60 秒内只能拿静态 SOP**——包括正在排障的
管理员自己；持续限流下"冷却 60s → 再失败 → 再 60s"可以无限循环。值班看到的指标是"降级常亮"，
真相是"某个用户并发太高"。这条链路的每一环都不是 bug，是**缺少一个决策**：
背压放在哪一层，降级的隔离维度是什么。

决策：

1. **准入放在入口，不在降级状态机上**：LLM 调用外包一层**全局信号量**（按上游并发上限的
   60–70% 设阈值，留出余量给半开探测与运维请求）+ 一层**每租户信号量**。拿不到许可先排队
   2–3 秒（覆盖一次正常回答的首字延迟），仍未拿到则**返回 429 + Retry-After**——
   明确的背压，不是静默排到超时。
2. **429 是背压，不是失败**：错误分类里"被自己限流"与"上游 429"必须分开；准入拒绝
   **不参与熔断开闸**（否则系统会被自己的准入打亮熔断，形成正反馈），并单独计数。
3. **降级作用域保持全局**（本 ADR 的核心取舍，**不**按租户复制状态机）。理由见下。
4. **熔断判据从"连续 N 次任意失败"改为"错误类型 + 滑动窗口失败率"**：embedding 抖动、
   客户端断开、被准入拒绝都不是"上游坏了"，把它们计入熔断会让一次无关抖动关掉全站生成能力。
5. **在途与拒绝必须可观测**：在途许可占用、排队时长、拒绝数、按租户的拒绝数进抓取面，
   并接门禁 6 的判据（"单人压不垮全站"要靠读数证明，不靠体感）。

理由：

① **背压与降级是两种信号，混在一起就会互相放大**。准入回答"现在能不能进来"，降级回答
   "进来之后用哪条链路"。没有准入时，唯一能拒绝流量的地方就是降级状态机——于是负载问题
   被写成了质量事故（全体降到 L2），而且不可自愈（持续负载 → 持续熔断）。
② **降级保持全局**的四条理由：
   - **语义**：降级档是"检索质量与门控口径"的全局声明（L1 期语义 Top-1 88.2%→70.6%、
     门控退为零召回级，见 ADR-0012）。按租户分别降级后，同一时刻不同租户跑不同的检索口径，
     "降级期的答案"不再可比，审计与复盘的口径直接分裂。
   - **资源**：L1 摘向量腿省的是**全站**的中间件与上游压力，这份压力不按租户隔离；
     按租户摘并不能省下对方没在用掉的资源。
   - **隔离该发生的位置**：真正意义上的"单人打爆"是**并发**问题，闸门在入口（决策 1）。
     让一个人先打亮全局降级、再把他隔到自己的降级分区里，是把伤害做完之后再补偿。
   - **成本**：每租户状态机 = 状态基数 × 租户数，而本项目**没有租户生命周期管理**
     （无开通/注销/配额分配流程），状态会随历史上出现过的 tenant 字符串永久泄漏。
③ **熔断只能由上游的失败触发**。"连续 3 次任意失败"在实测里已经被 embedding 抖动与客户端
   断开污染过（成功被写成失败 → 3 次即误开全局熔断，而 LLM 本身健康）。判据必须是
   "上游错误类型 + 失败率"，且 429 退避而非开闸。

备选与否决：

| 被否项 | 理由 |
| --- | --- |
| **每租户降级状态机**（per-tenant L0/L1/L2） | 见理由 ②：语义分裂、不省资源、隔离位置错、状态基数泄漏。它是"看起来更公平"的方案，实际把不可比变成了默认。 |
| 只做全局信号量，不做租户维度 | 一个租户就能吃满全局许可；"谁在打爆"仍要靠事后查审计，值班无法在 5 分钟内定位（门禁 6/10 都过不了）。 |
| 只做租户维度，不做全局 | 租户数 × 租户阈值 会超过上游真实上限——各自"合规"地合起来打爆上游。全局闸门是上游预算的唯一守门人。 |
| 无限排队（把请求堆在队列里等许可） | 内存与延迟双爆炸；SSE 客户端等不到东西会先断开，服务端却仍在排。排队必须有上限与超时。 |
| 用 Tomcat `maxConnections` 当准入 | 那是连接层上限，SSE 长连接会长期占住连接槽，与"同时有多少个 LLM 调用在跑"不是一回事。 |
| 在降级状态机上做限流 | 状态机是**观察者**（记录档位与转移），不是**守门人**；让它拒绝流量会把"质量取舍"与"容量控制"焊死，两者不再能独立调整。 |

后果：

- 门禁 6 的判据（"单人压不垮全站"）**依赖准入生效这一前提**：降级仍全局，若准入阈值配错，
  单人依然能把全局降级打亮。故该门禁的复核必须同时看"拒绝数/在途数读数"与"其他租户档位未变"，
  不能只看"没崩"。
- 配额与许可是两个维度，准入不替代配额：日配额是成本预算，信号量是并发背压。实施时**不得**
  在合并等待者上重复消耗配额（现行为是折叠前计数；那是历史实现，不在本 ADR 决策范围，
  但要与准入同批核对，避免"配额被准入 429 反噬"）。
- 上游预算成为显式常量：全局阈值必须与上游套餐并发上限对照着设，写进部署文档并由门禁 8
  （依赖/容量变化）复核时一起重看。
- 实施批次在 G1；G0 期间本条只作为**已知风险**出现在 README「运维就绪边界」与门禁文件里，
  不声称已缓解。
