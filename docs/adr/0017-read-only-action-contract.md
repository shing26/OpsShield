# 行动契约：只读、逐字抽取、fail-closed，网关不执行任何命令

状态：accepted（2026-10-10，随「四个深度优化点」ROI 排序第四项落地）

上下文：检索层已经给出"这次问题可能是什么"和"依据是哪几段"（refs 溯源是合同，ADR 系列
一贯口径），但运维读完答案后**下一步该跑什么命令**，仍然要自己从引用的 runbook 里去翻。
这带来三个具体缺口：

1. **答案止步于"是什么"，不到"怎么做"**。`rb-101~105` 本机辖区手册里写满了可执行的只读
   排查命令（`jstack`、`keytool -printcert`、`redis-cli INFO clients`），它们已经在 refs
   里被引用了，却被当作正文里的文本——用户要点进原文手动找。
2. **任意"补一步"都会立刻撞上 ADR-0013 的红线**。给排障系统加"建议执行"最自然的形态是
   反过来的：让模型生成一段命令清单。但那等于把"这条命令是不是写操作"的决定权交给整个
   系统里唯一没有静态可判性的部件，同时给"网关替用户动手"开了一道门。
3. **阈值不在语料里的那类问题没有出口**。判据可以包在协处理器/回调里，但那不是排障网关
   该管的事（ADR-0013：可信底座不是第 4 个 agent）。

三条事实同时为真：
- 语料里 448 chunks 中有 70 个闭合代码围栏、142 条命令候选；段名闸内（见下）37 个 chunk
  带围栏、49 条候选——**语料本来就自带可执行建议**，缺的只是结构化出口；
- 命令文本就是 refs 已经下发过的参考内容，抽出来不引入任何新的信息面、不需要新的权限闸；
- "是不是只读"是**词法可判**的，而模型生成不是。

用户对本条的约束（原话）：**"严格恪守 ADR-0013 的「只读、零写操作、非侵入式可信基座」原则，
Action Contract 仅输出「结构化只读行动契约」，网关自身坚决不引入任何物理写操作与主动执行回路。"**

候选方案三条：

| 方案 | 形态 | 否决理由 |
| --- | --- | --- |
| A 让 LLM 生成命令清单 | prompt 里追加"请给出可执行命令"schema | 把"会不会顺手写个 `KILL`"的决定权交给唯一没有静态可判性的部件；且生成内容非原文，无从逐字核对——幻觉面直接长在"可信"两个字上。 |
| B 网关执行命令、回填结果 | 起个 executor，接受前端点按执行 | 直接把 ADR-0013 从"可信底座"改写成"agent"。物理写操作与主动执行回路都是本 ADR 明确禁止的范畴，且跨租户/密级的执行鉴权要另起一套防线。 |
| C 只读、逐字抽取、fail-closed 策略 | 词法抽取 + 四层策略 + 计数器 | 采纳。 |

决策：**契约是"抽"出来的，不是"生成"出来的；网关只描述，从不执行。**

四层判据（`action/ReadOnlyCommandPolicy.java`），任一层不过即整条判拒：

1. **工具白名单（闭集）**：第一 token 必须在表内。`rm`/`mv`/`chmod`/`taskkill`/`mysql`
   （客户端语义随语句走，词法层收敛不了）/`tcpdump`（默认落 pcap）/`wget`（默认写文件）
   一律不在表内——这是最主要的一道闸。
2. **多态工具的子动词闭集**：`kubectl`/`docker`/`git`/`systemctl`/`redis-cli`/`jcmd` 等
   单二进制多语义工具，按「动词（必要时再看子动词）」收敛。`kubectl delete`、
   `redis-cli FLUSHALL`、`git push` 死在这一层。
3. **外壳/执行型前缀递归校验**：`sh -c '…'`、`ssh host '…'`、`kubectl exec … -- …`、
   `docker exec … -- …` **不许整体放行**——外壳里装的负载要用同一套策略再判一遍
   （`MAX_DEPTH=3` 防 `sh -c 'sh -c …'` 嵌套炸弹）。负载判不过，外壳一起拒。
4. **旗标与重定向**：命令替换（`$(…)`/反引号/`system(`/`popen(`/`exec(`）是唯一能把写操作
   藏进"已核准工具"参数里的通道，一律判拒；重定向目标只允许 `/dev/null` 或 fd
   （`2>/dev/null` 无害，`> /tmp/x` 是写文件）。

**两道闸的先后顺序刻意如此**（`action/ReadOnlyActionExtractor.java`）：

- **段名闸在前**：只认标题含「排查」的段，且排除「陷阱/误判」——语料里 `taskkill`、`KILL`、
  重启中间件都住「止损操作」「修复措施」这类段里，先按段排除，比逐条判更省也更稳。
- **命令闸在后**：段内每条候选再过四层策略，判不过→丢弃并计数。

**判拒必须可观测**：静默丢弃会让"某段一条建议都没有"与"压根没抽"无法区分。故
`aiops.guard.action_commands_rejected` 计数器只进 Prometheus，不进 `/state` 面板契约
（同 ADR-0016 的命名与暴露面口径）。

**活体复核**（`offline/action_contract_probe.py`，用户对本项的第二个要求："探针只读复核契约"）：
单测锁的是抽取器在**离线语料**上的不变式，而"契约到了线上流量上还成立吗"是另一回事——帧形状、
回放保真、跨租户不出界这三件事单测结构上就做不到。故探针把同一批不变式搬到 live，逐条钉住：
`done` 帧必带 `actions` 键（空表合法、缺键不合法）、每条命令逐字于 `ref` 指向的 chunk 原文、
契约 ⊆ 引用（`ref` 命中本轮 refs 且 breadcrumb/service 同源、段名闸、写操作段黑名单、
编号 1..N）、破坏性形态绊线（与策略允许清单角色不同：策略管准入，绊线管末端）、同一 query
重发后 actions 逐条相同且 `cache_hit` 非 none、每条 action/ref 的 chunk 都属于调用方租户、
拒绝计数器单调不减。**探针自己也恪守 ADR-0013**：只读 login + chat/stream + actuator/prometheus，
`/admin` 一条不打——连 `cache/flush` 也不打（没有判据需要它，而它会改变被测系统状态）；语料
原文本地只读，HTTP 复用 `localapi` 的环回断言。判据极性（改坏必红）由
`offline/tests/test_action_contract_probe.py` 用合成坏响应逐条钉住，变异验证五项全红、复原全绿。
探针刻意**不锁单请求产额**——那是上文那条软上限的事，锁了会让探针随 top-3 抖动假红。

**覆盖面是刻意上限而非疏漏**（2026-10-10 活语料取证，448 chunk / 70 围栏 / 142 候选，
段名闸内 37 chunk 带围栏、49 候选）：抽出 **41 条**、判拒 **8 条**。判拒的 8 条各有名有姓：
rb-002 的 `FOR UPDATE NOWAIT` 1 条（行锁=写）、rb-004 的 `sh mqadmin …` 2 条（外壳负载是
任意 Java 工具）、rb-007 的伪代码 2 条（`->` 续行不是命令）、rb-009 的 PromQL 与
`kubectl exec … java …` 2 条（查询语无命令形态 / 容器内跑解释器）、rb-013 的
`curl -X POST` 1 条（显式方法改写）。**8 条全部是"给错一条"级别的真拒，没有一条是误伤**
（误伤是另一回事，见下面的软上限表）。段名闸全关时可抽数会向 142 逼近，所以回归锁把上限
定在 120——**闸一旦被悄悄放开，这条测试必红**。

**但这 41 条是"抽取能力"的上限，不是"单次请求的产额"**——两者差着一个 `final-top-k`。
语料扫描喂的是全部 37 个闸内 chunk；线上一次请求喂给抽取器的，只有本次**引用的 top-3**
（`ReadOnlyActionExtractor.extract(outcome.chunks())`，而 `outcome.chunks()` 就是 refs
那一份）。所以 **"契约 ⊆ 引用"是构造保证**，不靠约定；代价是契约多寡被 top-3 卡住。

**单次请求产额的实测**（2026-10-10，live；`/api/v1/admin/cache/flush` 清掉 L1+L2 后逐个跑，
11 个固定查询形状、错误码均为语料里真实存在的码、11 个读到的 `cache_hit` 全为 `none`）：
**6 / 11 出非空契约，共 9 条动作**。而这 11 个形状的**目标文档全都有 2~3 个可抽的排查段叶
chunk**——语料不是瓶颈，top-3 才是。复现口径（逐条 POST `/api/v1/copilot/chat/stream`，
`source: manual`，先 flush，读 `done` 帧的 `actions` 长度）：`数据库死锁 50013_DB_DEADLOCK 怎么排查`、
`订单创建超时 50012_DB_TIMEOUT 定位慢 SQL`、`Redis 超时 50021_REDIS_TIMEOUT 排查`、
`Redis 连接被拒 50022_REDIS_CONN_REFUSED 排查`、`证书过期 50111_CERT_EXPIRING 排查`、
`OSS 上传 50061_OSS_UPLOAD_DENIED 排查`、`支付网关 502 50041_PAY_GATEWAY_502 排查`、
`mq 消费积压 50031_MQ_CONSUME_LAG 排查`、`jstack 看线程池打满`、
`ES 索引不存在 50051_ES_INDEX_MISSING 搜索不到 排查`、`pod OOMKilled 容器被 kill 排查`。
落空那 5 个的引用面包屑把机制指得很具体：

| 查询 | 引用的三段 | 差在哪 |
| --- | --- | --- |
| `50013_DB_DEADLOCK 怎么排查` | 文档标题 / `排查步骤`（段头）/ `适用症状` | 命令在 `排查步骤 > 第N步` 叶里，叶排在第 4 之后 |
| `50021_REDIS_TIMEOUT 排查` | 文档标题 / `排查步骤`（段头）/ `适用症状` | 同上 |
| `50022_REDIS_CONN_REFUSED 排查` | 复盘标题 / 手册标题 / `事故摘要` | 被同码的**复盘文档**挤占，手册的叶没进前三 |
| `50041_PAY_GATEWAY_502 排查` | 手册标题 / 复盘标题 / `排查步骤`（段头） | 手册的槽被同文档的标题与段头自己占了 |
| `50051_ES_INDEX_MISSING …排查` | `搜索索引排查（50051…`（段头，两份）/ 文档标题 | 段头本身在闸内（含"排查"）但不带命令；叶排在段头之后 |

命中的形状恰好都引用了**编号叶 chunk**（`排查步骤 > 第二步：定位慢 SQL`、
`排查步骤 > 第一步：查证书有效期`）。文档标题、段头、症状摘要这类 chunk 语义权重低但词面
重合高，把 `final-top-k: 3` 的三个槽占满，命令所在的叶就落到第 4 名开外。11 个形状里 9 个
走了**快路径**（精确错误码命中 ES Top-1 → 跳过精排、直接取 RRF 序，`HybridSearchService:67`），
而**唯一两个没过快路径的**（`jstack 看线程池打满`、`pod OOMKilled`）**都命中了**——n=2，
只能算方向一致的信号而非证明，但它与"精排会把叶重排进前三"的解释相容，是本次留下的待查线索。

本条不立项修复，按闹钟表登记（OPS §5「行动契约的 top-3 产额」）：两个候选动作各有代价——
抬高 `final-top-k` 要连带重跑评测并重新登记现役口径那组数字（精确 Top-1 100% / 语义 Hit@3
100% / 语义 Top-1 88.2%，README 与面板口径都引它），而同文档兄弟段扩张（"引用的手册里其他
排查段的命令也一并下发"）会**打破"契约 ⊆ 引用"这条构造保证**，等于给未引用的原文新开一个
权限放行口，须先做一次显式的权限复核。

**本 ADR 落地时自己抓到并修掉的一个抽取缺陷**：rb-001 的
`EXPLAIN SELECT ... ;  -- 对疑似 SQL 执行，重点看 key 与 rows` 整条判拒。根因不是策略严，
而是策略按 `;` 切段后，尾随的行内注释变成一段"命令"，首 token `--` 不在工具表里。手册里
最有用的那条 EXPLAIN 就这么消失了。修法在抽取侧（`dropAfterTerminator`）：只剥语句收尾符
之后的尾注，语句体内的注释不动。修后该条进契约、判拒数 9 → 8。这正是"覆盖面上限要逐条
复核"的价值——上限应当来自判据，不该来自解析疏漏。

否决项：

| 被否项 | 理由 |
| --- | --- |
| 让 LLM 生成命令清单 | 见方案 A。幻觉面直接长在"可信"上，且无从逐字核对。 |
| 网关提供"一键执行"入口/执行器 | 见方案 B。ADR-0013 红线，且"物理写操作 + 主动执行回路"双禁。 |
| 契约写入 `/state` 面板契约 | snapshot 的键是面板磁贴面（`check_panel_contract.sh` 双向锁死），塞键就得同步改磁贴，把观测需求变成 UI 需求。 |
| 用黑名单版策略（"非写即可过"） | 白名单漏一个 PUA 就过去了，黑名单漏一个才过去；且形态未收敛的 `mysql` 客户端、`java -cp`、`sh mqadmin` 这类能跑任意语句的入口，黑名单写不完。语料实测 9 条判拒里有 4 条正是黑名单形态挡不住的。 |
| 为老缓存写迁移脚本把 `actions` 补进去 | L1/L2 payload 带的是**当前请求**新抽的契约；旧 JSON 反序列化后 `actions` 为 null，走 `actionsOrEmpty()` 取空表即可，2h TTL 内自然换代（同 ADR-0006 的换代思路）。 |

后果：

- **协议面**：`done` 帧恒带 `actions` 键（空表也是 `[]`，客户端不必判存在性）；
  `error` 帧沿用旧形态——只在非空时带 `refs`/`actions`（rb-111 的 error 帧形状不变）。
  契约在**异常帧也送达**：`ChatOrchestrator` 内层 catch 不自己发帧，只把已到手的 refs/
  actions 挂到 `FailedWithContract` 上，由 `submit` 唯一 catch 出口交 `sink.error(...)`。
  生成侧失败不该连坐吞掉"这次能做什么"——那是本系统与纯生成式问答的唯一区别。
- **OpenAI 兼容面**（`/v1` 协议没有结构化帧位）：契约与 refs 同思路降级为答案尾部
  markdown；空契约不发帧（空 `content` 帧会让客户端多渲染一跳，
  `OpenAiChatSinkTest.frameSequenceMatchesOpenaiContract` 5 帧断言 + 新增
  `emptyContractEmitsNoFrame` 3 帧断言双向锁死）。
- **troubleshoot.html**：答案下方渲染编号行动清单，每条带语言标、mono 命令、来源面包屑、
  复制按钮，卡片头固定一句「只读 · 网关不执行」。
- 单测 197 → 223：策略变异矩阵 12 条（正例含 `docker exec -it … cat …`；
  反例含 exec 负载按 `[OPTIONS] CONTAINER COMMAND` 语法定位后的 `rm -rf`）、
  抽取器 10 条（段名闸/零幻觉/行内注释剥离/活语料扫描）、编排与协议 4 条
  （老缓存无 actions 空表回放、LLM 失败契约照送、异常帧带契约、空契约不发帧）。
- ADR 计数 16 → 17；README 的 ADR 与单测数字由 `offline/doc_numbers.py` 现算比对，
  改字是被门闩要求的。
- **面试话术**：从"答案带引用"升级为"答案带**可复制的只读命令清单**，且每条逐字出自
  已引用原文，判拒可观测"。可对着 `/actuator/prometheus` 的
  `aiops_guard_action_commands_rejected` 讲 fail-closed 的取舍。

**2026-10-11 评审批（Reviewer-Security 全量审查后收紧，单测 223 → 229）**：审查发现四组可让
"只读契约"名不副实的绕过，全部修复并钉回归锁——① 纯读工具的旗标级写面：`env` 本身是执行器
（`env rm -rf /` 首词过白名单）、`sort -o`/`openssl x509 -out` 落盘、`date -s` 改时钟、
`dmesg -C` 清缓冲、`journalctl --vacuum-*` 删归档、`hostname <名>` 改名、`ifconfig` 改网卡
——分别移出白名单或补旗标闭集（认不出即拒）；② 进程替换 `<(…)`/`>(…)`/`=(…)` 与 `$(…)` 同罪
——替换体里的命令会真实执行，argv 首词是 cat 挡不住；③ `ssh` 取值旗标闭集：旧判据"跳过全部
`-` 再跳一个 host"会把 `ssh -i key host rm -rf /` 的负载整体漏校验——改为闭集跳值、host 之后
全量递归、`-o`/`-L`/`-R`/`-D`/`-W`/`-J` 等隧道与任意配置旗标出现即拒；④ 占位符掩码只认
**纯 `<名>` 段**——`<in>out` 的 `>` 是真重定向（bash 语义下 stdout 落盘），掩掉它就是漏判。
Java 与 Python 探针双镜像同步，变异验证三路（进程替换标记 / ssh 未知旗标 / env 回白名单）全红
后复原全绿。语料零翻转：现役 41 条契约、8 条判拒原样成立。

**已登记的软上限（诚实记账，未进债表）**：

| 上限 | 形态 | 处置 |
| --- | --- | --- |
| SQL 字符串字面量误伤 | `SELECT * FROM t WHERE op='DELETE'` 被整条判拒 | 刻意接受：少给一条建议，好过给错一条。真要解析字面量等于在词法层写个 SQL parser。 |
| PromQL 等查询语无命令形态 | `container_memory_working_set_bytes{…}` 整块丢弃 | 无 `bash`/`sql` 围栏形态，无从安全判定；语料里这类查询写在散文里。 |
| awk 的字段语法撞第 4 层 | `awk '{print $NF}'` 判拒（`$(` 是命令替换标记） | 与命令替换共用同一个词法标记，无法在不放开 `$(` 的前提下区分。 |
| 进程替换的合法读用法 | `diff <(sort a) <(sort b)` 判拒（2026-10-11 起） | 与命令替换共用同一标记通道；替换体是任意命令，词法层区分不开，宁拒。 |
| ssh 旗标闭集外形态 | `ssh -v`/`-4` 等闭集外旗标、`-o`/`-L`/`-J` 隧道与代理一律判拒 | 旗标值是任意配置或端口转发，词法层收敛不了；语料零使用。 |
| 多语句 SQL 围栏并成一条烂语句 | `SELECT 1;` 与后续行并成混合体 | 行内 `;` 连同其后注释一起被切（收尾符剥离），判拒不漏（写关键字仍在），只是建议语法烂——质量项非安全项。 |
