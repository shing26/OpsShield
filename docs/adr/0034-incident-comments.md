# ADR-0034：事故评论（追加式讨论与 @）

- 状态：已采纳（2026-11-22）
- 相关：ADR-0007（单轮无会话）、ADR-0032（事故持久化）、ADR-0033（责任流转）、
  契约 [plans/incident-collaboration-accept.md](../plans/incident-collaboration-accept.md)

## 背景

ADR-0032 / ADR-0033 之后，事故单能持久化、能转交、能按 SLA 提醒，但**没有"人对人说话"的位置**：
想补一句"这条命令我执行过了，连接数已回落"，只能塞进 `diagnosis` 或 `timeline`。
两者都是**客户端整段覆盖写**的快照——两个协作者同时补记录时后写赢（ADR-0032 已登记该边界），
拿它当讨论区会丢话。

本切片补三件事：**追加式评论**、**服务端解析的 @**、**会话内未读角标**。
不做编辑/删除、富文本、附件、表情回应、线程回复、IM 推送与跨租户 @。

## 决策

1. **评论是 append-only 的对话事实**。新增 `incident_comments`（Flyway V7）与
   `POST /incidents/{id}/comments`，每次请求只 `INSERT` 一行，不读改写既有行。
   与 `timeline_json` 的**状态快照**语义刻意分开：并发 10 条评论必须 10 条都在，
   而时间线在同样的并发下会互相覆盖。没有 update / delete / 软删列——撤回要另立一轮设计。
2. **@ 由服务端从正文解析，客户端数组只作提示**。`mentions` 以正文里的 `@用户名` 为准，
   请求体的 `mentions` 数组不参与授权、不落库；否则前端改一个数组就能伪造点名。
   被点名者必须是本租户启用用户，否则 400 并**点名具体用户名**（不静默丢弃，
   否则被 @ 的人永远不知道）。同一评论去重，最多 10 人；落库为 JSON 数组。
   用户名允许 `-`（如 `sre-limited`）；email 形态（`a@b.com`）不误判为点名。
3. **权限与协作者同口径**。任何同租户、`authLevel>=1` 的用户都可评论，
   不需要 `created_by` / `owner` / `platform`；跨租户一律 404，不泄漏存在性。
   评论**不改变**事故状态、负责人、优先级，也**不写 timeline**——它只是对话。
4. **读取按 commentId 水位增量**。`GET /{id}/comments?since=<commentId>` 返回
   `{comments, nextSince}`，按 `(created_at, comment_id)` 升序，单次上限 100。
   左栏未读角标消费列表响应里的 `lastCommentId`（每单 `MAX(comment_id)`），
   不额外读正文、也不新增服务端已读表。
5. **正文与容量边界显式**。正文 trim 后 1..2000 字，空/超长 400；
   单事故 200 条，超出 409 并提示「请在结单备注里汇总」——讨论区不是结单台账。
6. **评论不进入检索 / LLM / 指纹 / 缓存键**。系统仍是单轮无会话（ADR-0007）：
   评论是给人看的，不是新的上下文来源。把它喂进检索会让"可溯源"变成"可被同事的话污染"。
7. **未读只在会话内**。水位存 `sessionStorage` 的 `opspilot.comments.seen`
   （incidentId → 已读 commentId），不落 `localStorage`、不新增服务端已读表、
   不做推送/浏览器通知。登录后的自动选中**不算已读**，只有用户显式打开事故单才清除角标。
8. **前端沿用夜班仪表台既有视觉语言**：讨论卡片位于「诊断分析」之后、「处置记录」之前，
   倒序显示最近 20 条；自己的评论用 accent 左边线、被 @ 到的评论用 warn 左边线区分；
   `@` 补全复用 `GET /assignees`；发送失败 toast 明示且**保留草稿**。不引入新依赖。

## 后果

- **V7 只新增一张表**：不修改既有表，旧代码不读它，失败 `git revert` 即可；
  自增主键用 `GENERATED BY DEFAULT AS IDENTITY`（H2 PostgreSQL 兼容模式不认 `AUTO_INCREMENT`）。
- **正文加宽走 V8，V7 不可再改**：V7 已在独立 commit（0cc2ab6）发布，`validate-on-migrate`
  会校验历史 checksum——回改 V7 会让已升级的库在启动时报 `Migration checksum mismatch`。
  因此 `body` 从 `VARCHAR(2000)` 加宽到 4000 由新增的
  `V8__incident_comments_body_width.sql` 完成：旧库只需前向补这一条迁移，无需重建。
- **单事故 200 条是服务端硬上限，事务内先锁事故行再 count 再 insert**：
  `SELECT ... FOR UPDATE` 把同一事故的追加串行化（H2 与 PostgreSQL 都支持），
  并发下不会突破。不用进程内锁——多实例部署下它无效。
  正文按 code point 校验 1..2000，列宽取 `VARCHAR(4000)` 覆盖最坏情况
  （2000 个代理对 = 4000 个 UTF-16 码元）；另加码元数兜底，超限一律 400，不到 JDBC 层。
- **`lastCommentId` 进了事故列表响应**：它只是未读角标的单调水位，不携带正文；
  列表查询因此多一条按租户分组的聚合，不改变检索链路与缓存键。
- **未读水位与会话同生命周期**：关掉标签页即丢失，下一次打开会重新显示"新"。
  这是有意的：没有服务端已读表，就不假装知道跨设备已读状态。
- **@ 解析失败会拒绝整条评论**：被点名者禁用/跨租户时返回 400，评论不会半落库。
  这比"静默丢弃 @、照常发出去"更吵，但避免了"以为叫到了人"。

## 备选方案

- **把评论塞进 timeline**：零 DDL，但时间线是整段覆盖写，并发会丢话，
  且与"状态快照"语义冲突，否决。
- **信任客户端传来的 mentions 数组**：实现最省事，但等于把点名授权交给前端；
  跨租户/禁用用户会被写进通知面，否决。
- **做编辑/删除或软删**：撤回涉及"谁有权撤、撤回后是否留痕、被 @ 的人是否要再通知"，
  不是本切片能收口的；先保持不可变，需要时另立契约。
- **服务端已读表 / 推送**：已读要跨设备一致就得建表与清理策略；推送要定收件人、频率、
  静默期。两者都会把一个可验收的协作切片变成通知系统，明确推迟。
- **把评论送入检索或 LLM 上下文**：违反 ADR-0007 的单轮无会话边界，且让同事的输入
  污染"可溯源"的答案，明确禁止。
