# 告警身份与查询指纹分开：指纹不吃人类可读文案

上下文：接入 Alertmanager 后首次实测（2026-10-17，qa 台账 §3.1）暴露一处契约错配——规则模板把
`{{ $value }}` 渲染进注解，同一条告警每次重发都带一个新数字；而指纹 `SHA256(service|env|归一化文本)`
直接吃 query 全文，于是**同一故障、同一条规则、同一份文案，每次重发都是一个新指纹**。后果链式：
L1 精确缓存永远 miss、Single-Flight 永不合并，而这两件事正是"告警风暴"这个核心场景的立足点。
`<N>` 归一化看似是防线，实际只保护自产告警（文案由脚本拼），保护不到别人的模板。

决策：**指纹不再从人类可读文案里推断身份**。新增可选请求体字段 `alertId`，由调用方（告警桥）从
规则身份四元组 `alertname|job|error_code|status` 定长派生；服务端新增 `FingerprintService.identity()`
对它做**不透明**哈希（不做文本归一化），L1 键与 SingleFlight 组键改吃这个身份。字段缺省时（人工提问、
既有自举告警源）逐字回退到原文本指纹，行为不变。

理由：① 真正稳定的东西是"哪条规则、哪个 job、哪个错误码、firing 还是 resolved"，那正是 Alertmanager
聚合时用的维度；② 身份由**调用方显式给出**，服务端不猜——这保住了"身份归一化的职责收在一处"；
③ `status` 参与身份是刻意的：firing 与 resolved 是两种语义，不该互相命中缓存。

备选与否决：**A 规则侧去抖**（注解不渲染 `$value`）——只在自家写得出规则的场景成立，治不了别人的规则，
且人读时失去量化信息，否决；**B 桥侧归一化**（query 合成后再跑一遍与 `FingerprintService` 同源的归一化）
——等于让桥替网关决定指纹身份，与服务端单一事实源冲突，且会连带掩掉错误码之外的语义差异，否决；
**C 服务端拆身份**——选定。

后果：产品面只多一个**可选** body 字段，无新端点、无新鉴权维度。踩到并已修的集成缺陷：线格式字段名
必须是 `alertId`（camelCase）——`ChatRequest` 走 Jackson 默认命名策略，发 snake_case 会被**静默忽略**、
身份退回文本指纹，第一轮验收因此出现过一次"假绿"（三条文案只差被 `<N>` 掩平的数字，文本指纹恰好也稳定）；
教训是 request body 的字段名必须用真实反序列化路径验。**仍未解（如实登记）**：L1 只缓存"成功且非 SOP"
的答案，故降级期与失败路径下**同身份**仍会重复穿透——那是独立问题，触发线见 OPS §5.1。
