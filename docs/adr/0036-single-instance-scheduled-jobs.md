# 定时任务与审计环沿用单实例假设，多副本前必须补分布式锁

## 上下文

ADR-0003 定下「单机单实例 + Single-Flight 用进程内 `CompletableFuture`」。此后三条切片
（ADR-0033 责任流转 / ADR-0034 评论 / ADR-0035 告警入口）都在这个假设上继续叠加了
**进程内调度**与**进程内审计环**，但没有一份文档把"哪些能力在多副本下仍然正确、
哪些会变语义"写清楚。结果是：所有单测与验收都在单实例下通过，而多副本部署的风险
只散落在代码注释里，没有可判定的触发线。

当前依赖单实例假设的位置：

- `IncidentSlaScanner`：`@Scheduled` 默认 60s（`opspilot.incident.sla.scan-interval-ms`）
  扫描未结单事故，把 `due_soon` / `breached` 写回 `incidents.sla_state`。
- `AlertIntakeService.scheduledCleanup`：`@Scheduled` 每日 03:17 清理告警台账
  （`last_seen < now-30d` 与每租户超 500 条）。
- `AuditService`：最近 200 条事件保存在进程内环，`GET /admin/audit/recent` 只读本进程。
- `SingleFlightRegistry`：同 `(tenant, fingerprint, authLevel)` 的并发只放 1 个 leader
  穿透 LLM，follower 回放 leader 的在途结果。

## 决策

**本 ADR 不改变任何运行时行为**，只把边界与触发线固定下来：在触发线被击穿之前，
继续按单实例部署；击穿之后按「到点必须做」一节改造，不得以"压测没出问题"为由跳步。

### 多副本下的真实影响（分级，不夸大）

| 位置 | 多副本后的行为 | 数据正确性 |
|---|---|---|
| SLA 扫描 | 每个副本都扫一遍；`transitionSla` 带旧状态做条件更新，只有 1 个副本能成功跃迁并落审计 | **正确**，只是 N 倍空转查询 |
| 告警清理 | `deleteOlderThan` / `deleteOverflow` 的排序与条件是确定性的，重复执行不会多删 | **正确**，但 `ev=admin action=alert_retention` 会重复 N 条 |
| 告警 upsert | `touch` → `insert`，主键冲突时捕获 `DuplicateKeyException` 再 `touch` | **正确**，DB 唯一键是最终仲裁 |
| 审计环 `/admin/audit/recent` | 每个副本只有自己的 200 条 | **不完整**：一次查询看不到其他副本的事件 |
| Single-Flight | 每个副本各自放行 1 个 leader | 结果一致，但 LLM 调用与延迟成本 × 副本数 |
| `lockIncident`（评论 200 条上限） | 走数据库 `SELECT ... FOR UPDATE` | **正确**，跨进程有效 |

结论：**数据层没有"多副本会写坏"的路径**；真正的缺口是
①审计不再是全局单一视图，②LLM 成本随副本数线性上升，③定时任务重复空转。

## 触发线

任一条成立即视为触发，必须进入「到点必须做」：

1. **部署副本数 > 1**——K8s `replicas > 1`、多机部署、或任一横向扩容动作。
2. **合规/追责要求"一次查询看到全部审计事件"**——`/admin/audit/recent` 的局部视图
   不再可接受（这是当前最硬的一条）。
3. **LLM 调用成本或 P95 延迟因重复穿透超出预算**——以 `aiops_*` 指标与账单为准，
   不靠感觉。
4. **需要 SLA 提醒在多副本下仍只发一次外部通知**——一旦接入 IM/邮件推送
   （当前明确未做），重复扫描会直接变成重复打扰。

与 OPS §5 的「多实例」债务行对齐：团队 >200 人或持续峰值 QPS >50 是**容量**触发线，
本 ADR 的触发线 1 是**拓扑**触发线；两者取先到者。

## 到点必须做

按成本从低到高，优先选前者：

1. **定时任务拆成独立单副本 worker**（首选）：主服务可多副本，
   `IncidentSlaScanner` / `AlertIntakeService.scheduledCleanup` 只在一个专用实例上启用
   （`@ConditionalOnProperty` 或独立 profile）。不改主服务任何语义。
2. **给定时任务加分布式锁**：若必须留在主服务内，用 DB 行锁（复用现有
   `SELECT ... FOR UPDATE` 模式）或 ShedLock；不引入仅 Redis 单点的锁
   （Redis 不可用时会静默失去互斥）。
3. **审计外置**：`/admin/audit/recent` 改为读持久化存储（带全局单调 seq），
   进程内环降级为缓存。审计的 WORM 副本（门禁 9）与读取路径要同源。
4. **Single-Flight 共享**：需要跨副本去重时，再引入 Redis Pub/Sub 或共享结果存储；
   在此之前接受"每副本各穿透一次"，但要在容量测算里显式计入。

**验收口径**：改造后必须有一条多副本（≥2）的实测证据，证明
①同一 SLA 跃迁只落 1 条审计、②`/admin/audit/recent` 能看到另一副本产生的事件、
③清理任务不产生重复 `alert_retention` 事件。只跑单实例不算数。

## 后果

- **单实例部署仍是当前唯一被验证的形态**：README 与部署文档不得暗示"直接加副本即可"。
- **SLA 与清理的幂等性来自数据库条件更新，不是来自调度器**：这一点让"先加副本、
  后补锁"不会立刻写坏数据，但也掩盖了审计与成本问题——所以触发线必须可观测。
- **审计环是已知的单点**：门禁 9 的 WORM 副本解决的是"防篡改"，不解决"多副本读取完整"。
- **不新增依赖**：本 ADR 只是把既有边界写死，`pom.xml` 与运行时零改动。

## 备选方案

- **现在就上分布式锁**：在没有多副本需求时引入 ShedLock/Redis 锁，增加一个故障面
  与一份运维依赖，收益为零；等触发线到了再做，且首选"独立 worker"而不是加锁。
- **把定时任务做成数据库触发器**：把业务逻辑下沉到 DDL，测试与迁移都更难，
  且 H2/PostgreSQL 方言差异会扩散；否决。
- **用 Redis 锁做唯一互斥**：Redis 不可用时锁失效会导致重复执行，且与 ADR-0003
  的"Redis 只做去重、不做协调"边界冲突；只在有第二道 DB 兜底时才考虑。
- **多副本 + 只靠"幂等所以无所谓"**：数据确实不会写坏，但审计不完整与 LLM 成本翻倍
  是真实后果；不接受用"幂等"掩盖。
