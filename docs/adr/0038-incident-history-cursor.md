# 事故历史使用键集分页，排序与筛选口径固定在服务端

## 上下文

事故列表此前硬编码返回最近 60 条（`ORDER BY updated_at DESC, incident_id DESC`），
前端又按 `slaRank()` 对同一数组二次排序，并在刷新与单条回填处 `slice(0, 60)`。
这带来三个已经可见的缺口：

- 第 61 条以后的事故永远看不到；
- 「进行中 / 已结单」由客户端过滤，分页后一页可能被过滤成空页；
- 顶栏「进行中 N」统计的是已加载数组，不是租户真实总数。

一旦引入分页，客户端二次排序会让追加页在视觉上跳回前排；因此顺序必须只有一个事实源。

## 决策

1. **键集（keyset）分页，禁止 OFFSET**。排序键为
   `(sla_rank ASC, updated_at DESC, incident_id DESC)`：
   `closed → 2 / breached → 0 / due_soon → 1 / 其余 → 2`，与旧前端 `slaRank()` 逐字一致。
   SQL 先在内层子查询算出 `sla_rank`，外层用展开比较：
   `rank > ? OR (rank = ? AND (updated_at < ? OR (updated_at = ? AND incident_id < ?)))`。
2. **游标不透明**：`base64url(v1|rank|epochMicros|incidentId|mine|status)`，无 padding。
   `updated_at` 用微秒而不是毫秒，避免同一毫秒的多行在边界处丢页。
   非法版本、段数、rank、ID 形状、筛选不一致一律 400；日志不记录游标原文。
3. **游标绑定筛选**：`mine/status` 必须与本次请求一致；换筛选必须重新拉第一页。
4. **游标不含 tenant、也不作为授权依据**：tenant 只来自 JWT。A 租户的游标在 B 租户请求里
   只会得到 B 自己的页，不扩大可见范围。
5. **`openCount` 独立统计**：本租户 `status='open'` 总数，不受 `mine/status/cursor` 影响，
   顶栏用它而不是已加载数组长度。
6. **前端只渲染服务端顺序**：加载更多按 `id` 去重追加，不重排；客户端最多保留 1000 条，
   到顶后按钮明示「已加载最近 1000 条，请用筛选缩小范围」。
7. **索引**：V11 只新增 `(tenant, updated_at, incident_id)`，服务租户扫描与并列定序；
   `sla_rank` 暂不物化。

## 否决项

- **`LIMIT ? OFFSET ?`**：深页越翻越慢，且并发写入会重复/漏行。
- **把 `sla_rank` 写进游标以外的前端排序**：顺序会出现两个事实源，追加页必然乱跳。
- **把 tenant 写进游标或拿游标做授权**：游标是可被客户端改写的不透明串，不能承担信任。
- **毫秒精度的时间键**：同一毫秒的多行会在 `updated_at < ?` 处整批丢失。
- **为可变排序键引入快照表/分布式锁**：本切片接受键集分页的快照边界（行被更新后可能
  不在后续页出现，刷新即最新），不为它增加一套存储与锁。

## 后果

- 旧客户端不传 `cursor/limit` 时行为等价第一页（默认 60 条），响应只新增字段，不改既有行形状。
- `FlywayMigrationTest` 同时覆盖空库与已有库，并断言 V11 索引列顺序。
- 性能边界已登记：单租户事故 > 5000 条或列表 p95 > 200ms 时，再评估把 `sla_rank`
  物化为列并建复合索引；本切片不提前施工。
