# ADR-0032：事故持久化与分配边界

- 状态：已采纳（2026-11-20）
- 相关：ADR-0005（H2 账号库）、ADR-0008（DB 是权限唯一真相）、ADR-0009（诚实性红线）、ADR-0026（准入）

## 背景

「事故」最初只存在于面板的 `localStorage`：换设备看不到、无法把责任交给别人、清缓存即丢。
它已经是用户心智里的业务对象（有编号、状态、处置记录），却没有任何服务端事实。

## 决策

1. **服务端建表** `incidents`（Flyway V5）。租户是硬隔离维度，所有 SQL 带 `tenant = ?`，
   tenant 只来自 JWT，永不来自请求体。
2. **快照而非规范化时间线**：`diagnosis_json` / `timeline_json` 以 CLOB 存 JSON。
   诊断结构还在演进，先保证"一次写入、整条读回"；等查询需求出现再拆表。
3. **创建幂等**：前端生成 `clientId`，唯一索引 `(tenant, client_id)`；重放返回原记录。
   ID 由服务端生成（`INC-MMdd-NNNN`），客户端不参与编号。
4. **分配限于同租户启用用户**：`assignees` 只列本租户；`owner` 校验存在性、启用状态与租户。
   跨租户返回 400 而不是"静默忽略"。
5. **责任动作单独授权**：结单/重开/改负责人/改优先级仅 `created_by`、当前 `owner` 或
   `role=platform`；其余同租户成员可协作写诊断与时间线。越权 403 并落 `ev=incident` 审计。
6. **前端只留选中项**：`localStorage` 仅保存 `opspilot.incidents.active`，业务数据一律走 API；
   写入失败必须 toast 明示（不允许"看起来保存了"）。

## 后果

- 未接入身份时左栏是"接入后加载"，而不是空列表——这是权限模型的直接结果。
- 事故快照可能与当前输入不一致（编辑输入未重跑诊断），UI 已有"结论对应旧输入"提示。
- 时间线是整段 JSON 覆盖写：同一事故的并发编辑是"后写赢"。当前单值班场景可接受；
  多写者场景到来时需改为事件追加 + 版本号。
- 不提供删除：结单是状态，不是删除；保留可追溯性（与审计一致）。

## 备选方案

- **localStorage + 手动导出/导入**：零后端改动，但解决不了多端与分配，否决。
- **按事件建表 `incident_events`**：查询能力更好，但当前只需要"整条渲染"，
  拆表会把一次保存变成多条事务与排序问题，推迟到有查询需求时再做。
- **允许跨租户分配**：违反租户硬隔离，直接否决。
