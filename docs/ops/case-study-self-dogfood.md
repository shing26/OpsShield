# 自证 case study：把自己当成第一个设计伙伴（2026-11-17）

> **读者**：产品/工程决策人，以及被问「有没有真实用户」的面试官。
> **用途**：外部设计伙伴不可得时，用项目自身的真实事故验证「事故签名 → 检索 → 引用 → 只读命令契约 → 审计」链路，并如实记录失败面。
> **边界**：单用户、单机、memory + mock、3 条查询。它证明机制与可审计性，**不**证明 live 答案质量、采纳率或 MTTR 改善。

## 1. 为什么这样验证

设计伙伴真正要回答的问题不是「系统能不能跑」，而是「值班的人敢不敢照着做」。本仓库恰好有一批
不可伪造的输入：本项目自己的事故史——H2 并发写损坏（`51103_H2_CONCURRENT_WRITE_CORRUPTION`）、
端口被别的项目占用、截断 jar、备份停摆 35 天、磁盘写满。这些事故已经写成复盘并回灌进语料
（[`rb-115-h2-corruption-recovery.md`](../../offline/corpus/runbooks/rb-115-h2-corruption-recovery.md)、
[`rb-103-port-occupied-wrong-service.md`](../../offline/corpus/runbooks/rb-103-port-occupied-wrong-service.md) 等），
因此可以把「当时的真实签名」原样再问一遍，看系统是否能把人带回正确的文档。

## 2. 实验设置

- 隔离实例：独立 H2 文件 `data/dogfood-users.mv.db`，端口 `8099`，不碰在用的 `data/users.mv.db`；
- `STORAGE_MODE=memory` + `DASHSCOPE_MODE=mock`，零外部依赖、零 API 成本；
- 账号 `sre-full`（`tenant-internal` / level 3 / platform），走真实 JWT 鉴权；
- 三条输入：两条精确事故签名（H2 损坏、8091 端口占用）+ 一条中文口语化查询；
- 证据：审计行固化在 [`evidence/dogfood-2026-11-17.jsonl`](evidence/dogfood-2026-11-17.jsonl)，可用下面命令复核：

```bash
python scripts/verify_audit_chain.py --allow-segment docs/ops/evidence/dogfood-2026-11-17.jsonl
```

## 3. 结果

| # | 输入（节选） | Top-1 引用 | 引用数 | 命令契约 | 耗时 | request_id |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | `MVStoreException: File is corrupted ...` | `rb-115`（正确） | 3 | **0** | 256ms | `94a408b1` |
| 2 | `Port 8091 was already in use.` | `rb-103`（正确） | 3 | **0** | 77ms | `b479c325` |
| 3 | `网关起不来，端口被别的项目占了...` | `rb-103`（正确）+ 处置段 + `rb-101` 端口表 | 3 | **0** | 114ms | `c5dc9585` |

**成立的部分**

- 精确错误码与异常文本走词法快路径，Top-1 直接命中对应复盘（3/3，n=3，不推广）；
- 中文口语化查询没有错误码，仍由混合检索把 `rb-103` 排到 Top-1，处置段排到 Top-2；
- 每条请求都留下审计行（`ev=chat`），含 `fp`、`refs`、`actions`、分段耗时、降级档位；
- 三次畸形请求（请求体契约不匹配）各留一行 `ev=invalid`，证明失败不是静默的；
- 证据文件 6 条审计行的哈希链校验 PASS（`--allow-segment`，0 条旧格式）。

**失败的部分（这次 dogfood 的真正产出）**

1. **只读命令契约产额为 0。** 两条最需要「下一步跑什么」的事故，`actions` 都是空。
   根因不是安全策略误杀，而是**产出面**：`ReadOnlyActionExtractor` 只认面包屑含「排查」的段，
   而 `rb-115` 的命令住在「排查步骤 > 第三步：评估可恢复性」，该 chunk 没进 Top-3；
   `rb-103` 的命令住在「处置」段，按设计整段不进契约。安全底线守住了，但值班的人拿不到命令。
   这正好给 [`OPS.md` §5](../../OPS.md) 已登记的「行动契约的 top-3 产额」触发线补上了第一组实证。
2. **第三引用跨服务串台。** 查 H2 损坏却把 `pm-004`（Session 服务 Redis 连接拒绝）带进 Top-3。
   引用本身越权过滤正确（level 3 才看得到生产拓扑），但「为什么给我看无关服务的复盘」会直接
   损伤信任。当前没有按 `service` 做引用收敛。
3. **mock 答案不可读。** mock 模板回显 chunk，触发逐字护栏 11 次/6 次，答案里出现重复的
   「此处原文较长，不便逐字展示」占位。这是 mock 轴的已知差异，不是 live 答案质量证据；
   但它放大了第 2 条：不该出现的引用会把模板答案带偏。
4. **语料漂移被这次查询撞到。** `rb-115` 仍写「schema.sql 启动自动建表」，而 schema 早已由
   Flyway V1 管理。这是 [`g1-remaining.md`](g1-remaining.md) §9 已登记的债务，本次自证说明它不是纸面问题。

## 4. 产品决策

| 优先级 | 动作 | 判据 |
| --- | --- | --- |
| P0 | 提高命令契约产额：按「步骤」粒度切 chunk，或在精确码快路径上强制纳入该文档的排查段；不改「清单 ⊆ 引用」约束 | 为 `rb-115` / `rb-103` 各加一条 golden，要求 `actions ≥ 1` 且命令逐字存在于引用原文 |
| P1 | 引用按服务收敛：同服务加权，跨服务引用需要查询里的显式信号；至少把「引用服务与 Top-1 不一致」做成可观测计数 | 同一批 3 条查询的跨服务引用数下降，且不引入漏检 |
| P1 | 修复 `rb-115` 的 Flyway 措辞并按 [`postmortem-draft.md`](postmortem-draft.md) 的清单重建 chunks / 评测 / reingest | provenance 同代校验通过，golden 不漂移 |
| P2 | 面板在 mock 模式显式标注「仅演示链路，不代表答案质量」；下一次 dogfood 用 `/api/v1/copilot/feedback` 记录 up/down | 审计出现 `ev=feedback`，`aiops_feedback_total` 有非零基线 |

## 5. 这次自证证明了什么、没证明什么

- **证明**：在真实事故签名上，检索能定位正确复盘；鉴权/密级过滤生效；失败请求有审计；
  审计链可验证；命令契约的**安全**没有破，但**产额**是产品缺口。
- **没证明**：live 生成质量、真实值班者的采纳率、MTTR 改善、多租户生产形态。
- **下一步**：同样的三条查询切到 live 后端重跑，记录 refs 与 actions 的差异；再请一位没参与开发的
  SRE 盲评「会不会照着命令做」。两次结果都进本文件，不覆盖旧行。

## 6. 立场

拿不到外部设计伙伴时，最诚实的做法不是把 demo 包装成产品，而是**把自己变成第一个会挑刺的用户**：
用真实事故提问，记录哪里有用、哪里没用。这次的结果是「定位对了，动作没给出来」——这比再多的
机制指标都更接近产品问题本身。
