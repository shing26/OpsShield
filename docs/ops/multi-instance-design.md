# 多实例改造设计（设计稿，未实现——对应 OPS §5「多实例」触发线）

> 2026-11-02。本文回答"如果要拆单实例，每一处进程内状态怎么改、代价是什么、什么被否决"。
> 触发线（OPS §5 原文口径）：**团队规模 / 峰值 QPS** 到点才做；本文的存在意义是把"到点之后
> 要付的账"从模糊变成清单，同时服务一个当下需求——面试与评审中"单实例假设"被追问时，
> 每一条都有可指的改造路径。**本文不是 ADR**：改造未启动、无决策被推翻，ADR-0003 仍然有效。
> 压测依据见 [../load/reports/bottleneck_es_pool.md](../load/reports/bottleneck_es_pool.md)。

## 1. 现状盘点：哪些状态在进程内（代码事实）

| 状态 | 位置 | 多实例下的行为 |
| --- | --- | --- |
| SingleFlight 合并注册表 | `storm/SingleFlightRegistry`（ADR-0003 有意进程内） | 合并率按实例数 1/N 衰减：风暴 500 并发打到 3 实例 → 3 次 LLM 而非 1 次 |
| L1 精确缓存 | `cache/L1CacheService`（本地） | 各实例冷启动各自miss，命中率摊薄；无正确性问题（L1 之后有 L2） |
| 降级状态机 | `resilience/DegradationStateMachine`（AtomicInteger + 内存档位） | 各实例独立升降档；同一时刻可能 L0/L1 并存；审计 `degrade_transition` 每实例各记各的 |
| inflight 计数 | 同上（`degrade.enter/exit`） | 阈值 40 语义变成"单实例在途"而非"系统在途"；且本轮压测已证明单实例下 inflight 触发线本就不可达（§4） |
| 审计哈希链 | 每实例自己的 seq/prev_hash 链 | 多实例并行写审计存储 → 链分叉，`verify_audit_chain` 按单链校验会假红 |
| SOP 预热/补灌 | `IngestionRunner` 启动时 | N 实例重复预热（幂等无害）；但 **reingest 是全局换别名动作，多实例并发 reingest 会竞态** |
| 已共享（无需改） | 配额（Redis INCR+TTL）、滑动窗口（Redisson）、L2（Redis+Qdrant）、JWT（无状态+查库吊销） | — |

## 2. 改造路径（按"改了才能正确"→"改了才划算"排序）

### 2.1 降级状态机：状态外置到 Redis（正确性问题，P0）

档位是全局事实（上游 LLM 挂了对所有实例都挂）。改法：档位 + 冷却期存 Redis 单 key，
转移用 Lua 原子读改写并落审计；本地每请求读（可 1s 微缓存）。半开自愈逻辑不变，
探测权归属改为"冷却到期后全局放行一个探测请求"（Redis 计数器抢探测权）。
被否方案：各实例独立状态机——看似简单，但风暴期实例间档位漂移会让"降级覆盖率"不可解释，
审计与面板口径直接坏掉。

### 2.2 审计链：分叉治理（正确性问题，P0）

两选一：① 链上移——审计写 Redis Stream，由单消费者落盘并维护全局链（实现最小，
代价是审计多一跳、消费进程成为可用性依赖）；② 链改树——per-instance 链 + 周期性
checkpoint 合并（无中心依赖，校验器复杂度上升）。**倾向 ①**：WORM 门禁已按"单链+副本验链"
取证，改树会连锁改门禁 9 的验收脚本。

### 2.3 SingleFlight：跨实例合并（收益问题，P1）

路径：dedup key 上 Redis SETNX 抢 leader（TTL=LLM 超时），follower 订阅完成事件
（pub/sub 或轮询 L2 写入），命中即回放。**代价要如实说**：跨实例合并引入一次 Redis RTT
（内网 ~1ms，相对 LLM 秒级可忽略），但**风暴合并率从"确定性 1 次"降为"leader 竞争成功率"**，
SETNX 失败重试窗口内的重复调用无法归零。被否方案：粘性 LB 按 fingerprint 路由——
保留进程内 SingleFlight 全部语义且零新组件，但依赖 LB hash 能力，且实例扩缩容时重排会
短暂打穿；作为**过渡形态先行**是合理的（LB 支持 hash 则先粘性，不划算再上 SETNX）。

### 2.4 L1 缓存：不改（P2）

L1 miss 落到 L2（共享），正确性由层次结构保证；多实例下 L1 命中率摊薄是**容量问题**，
等实测摊薄超过阈值再考虑失效广播（pub/sub invalidation），现在做是过早优化。

### 2.5 reingest 与启动动作：单写者锁（P1）

`POST /admin/reingest` 与 SOP 补灌必须全局串行：Redis 分布式锁（Redisson 已在依赖内），
持锁期间其他实例的 reingest 请求 409。不改则别名切换竞态在多实例下是数据事故。

### 2.6 准入与降级的阈值口径（设计修正，随 2.1 一并做）

本轮压测实证：单实例下 `inflight-threshold: 40` 已被准入（全局 32）压到不可达；多实例后
"in-flight"语义进一步稀释。改法二选一：① 降级触发线改为**准入占用率**（如全局 permits
占用 >80% 持续 N 秒 → L1）；② inflight 聚合到 Redis 全局计数。倾向 ①——准入信号
本来就是全局的，且不受实例数影响。

## 3. 部署形态与不做的事

- 形态：LB（无粘性，JWT 无状态）→ N × 网关（无状态化后）→ 共享 Redis/Qdrant/ES + 单写者 reingest。
  systemd/备份/监控门禁不受影响（它们按实例自治）。
- **不做**：分布式追踪接线（W3C traceparent 触发线在 OPS §5.1，独立于本改造）、多区域、
  L2 分片——各自有独立的触发线，别搭车。

## 4. 验收口径（到点时按此验收，避免"起了两个实例就算多实例"）

1. 风暴演练（500 并发同指纹）经 LB 打 2 实例：LLM 调用 ≤ 预期合并率上限（粘性形态 ≤1，SETNX 形态按 §2.3 代价公式）；
2. 杀一实例：另一实例 0 感知（降级档位、L2 命中、审计连续性三项核对）；
3. 双实例并发 reingest：一个成功一个 409，别名无竞态；
4. 审计校验器在多写者形态下全链 PASS；
5. 准入/降级新口径在双实例下实测行使一次（沿用本轮 stub 压测协议即可）。
