# 生产门禁与演练（M0 / M1）

> **读者**：发布决定人（M0/M1 的验收人）与值班 SRE。
> **用途**：把「生产就绪」从形容词变成可复核的判据——十条门禁、两条运行档、六类演练、值班五分钟判据。
> **判据来源**：[2026-10-22 运维审查](../qa/2026-10-22-ops-readiness-review.md) §7 出口 B 的十条门禁；
> 本文件负责把它们展开成**命令、证据落点与结论**，并保管复核记录。
> **与其他文档的分工**：README「运维就绪边界」只做索引；日常动作在 [OPS.md](../../OPS.md)；
> 债务触发线在 OPS §5 / §5.1。三处冲突时以本文件为准（它带日期与复核记录，其余两处不带）。
> **本文件不手写会漂的数字**：用例数、语料数、指标值由 `offline/doc_numbers.py` 与产物守着；
> 本文件只写判据与结论，引用数字时指到产物。

## 1. 判定方式

### 1.1 两条运行档

| 档位 | 依赖 | 耗时量级 | 谁跑 / 何时跑 | 失败后果 |
| --- | --- | --- | --- | --- |
| **fast** | 零凭据、零中间件（memory + mock 即可）、不碰生产数据 | 分钟级 | 提交前自查 + CI；每条门禁复核的第一遍 | 阻断合并 |
| **full** | 活体栈（compose 全栈或宿主裸进程）+ 演练环境 + 一次真实注入 | 小时级 | 发布前，由验收人主持 | 阻断发布（除非走 1.3 的黄色通道） |

**fast 不能替代 full**：门禁 1/2/4/5/6/9/10 的判据里有「运行事实」（备份真的成功、告警真的到人、演练真的做了一次），
这些只能由 full 档回答。fast 档只回答「配置与代码还在位」。

### 1.2 结论只有三档

| 结论 | 定义 | 后续 |
| --- | --- | --- |
| **绿** | 判据全部满足，证据落点可指到（文件路径 / 命令输出 / 读数），且证据产生时间在本轮复核窗口内 | 记入 §4，可发布 |
| **黄** | 判据可满足但有明确边界（例：单机形态下的已知单点），且**已登记负责人 + 到期日** | 记入 §4，可有条件发布；到期未清转红 |
| **红** | 任一判据不满足，或证据只能口头给出（"已修"、"应该没问题"） | 阻断发布 |

**证据纪律**：每条结论必须指到「一个路径 + 一个时间点 + 一条可重跑的命令」。
接受 `logs/` 下的产物、Prometheus 读数、审计行、截图（截图必须带系统时间与主机名）。
不接受"我本地试过没问题"——这正是 2026-10-22 审查里被证伪的那类陈述（备份"每日跑"，实际停摆 35 天）。

### 1.3 复核记录

每次复核在 §4 追加一行；**不覆盖旧行**。基线行固定为 2026-10-22 的审查结论。

## 3. 六类演练

**通用纪律**

- 只在**隔离环境**做（独立目录 + 独立数据卷 + 独立端口；不要拿正在被人使用的实例做注入）。
- 不打印、不复制任何凭据值；需要 token 走 `scripts/console_token.sh` 取。
- 每次演练固定四段：**注入 → 判据（≤5 分钟）→ 恢复 → 留痕**；留痕写进 §4。
- **判据不是"服务还能用"**，而是"人能不能在 5 分钟内说清哪一层坏了"。恢复成功不算过；**定位成功**才算过。

### 3.1 停网关

| 段 | 内容 |
| --- | --- |
| 目的 | 验证「被监控对象死了」这件事本身有没有人知道（这是自监控最容易漏的一类） |
| 注入 | 隔离环境里停网关进程 / `docker compose stop gateway` |
| 判据（≤5 分钟） | ① 抓取面 `up` 类指标转为 0 且有人收到通知；② 通知内容指到「网关不可达」而非泛泛的"异常"；③ 值班按 §5.2 能在 5 分钟内给出「网关还是中间件还是网络」的结论 |
| 恢复 | 起回网关，确认抓取面恢复、探针重新绿 |
| 常见翻车 | 监控栈与被监控对象同生共死（同机、同 compose、同重启策略）——此时"网关死了"和"监控也死了"同时发生，演练会**假绿**：注入后没有任何信号，却被记成"没告警=没异常" |

### 3.2 停 Redis

| 段 | 内容 |
| --- | --- |
| 目的 | 验证热路径硬依赖失效时的**行为可解释性**：是 5xx、是降级、还是静默变慢 |
| 注入 | `docker compose stop redis`（隔离栈） |
| 判据（≤5 分钟） | ① 排障请求的失败形态是明确的 5xx/降级，而不是无限等待；② 审计里能读出失败类别；③ 通知到人；④ 值班能在 5 分钟内区分「Redis 挂了」与「LLM 挂了」——两者的症状都是"排障变慢/报错" |
| 恢复 | 起回 Redis，确认配额/登录失败计数/缓存多级行为回到基线；注意 Redis 无持久化时重启会清空当日配额与锁定计数（OPS §10 已登记） |
| 已知边界 | 淘汰策略会清掉静态兜底数据（SOP），故 Redis 恢复后要确认兜底清单被重新预热，否则 L2 期答案会退化成空 |

### 3.3 磁盘满

| 段 | 内容 |
| --- | --- |
| 目的 | 验证「写不进去」时系统是降级还是静默丢证据——审计与账号库同盘时，先坏的是证据 |
| 注入 | 在**演练盘**上造填充文件：Windows `fsutil file createnew D:\drill\fill.bin <字节数>`；Linux `fallocate -l 2G /tmp/drill/fill.bin`。填充到剩 ~50MB 即停（不要把整机盘写满，尤其别写系统盘） |
| 判据（≤5 分钟） | ① 磁盘水位告警到人；② 发现"写失败"的那一层可指认（审计？账号库？日志？）；③ **不能出现"接口 200 但证据静默丢失"**——若出现，该次演练判**红**（这条是本项目实测过的真实失效：日志写失败的异常被吞，面板仍展示未落盘的事件） |
| 恢复 | 删填充文件，确认写入恢复、审计继续追加（不是从此静默） |
| 留痕 | 记录填充前后的剩余空间、告警时间、恢复时间 |

### 3.4 断客户端

| 段 | 内容 |
| --- | --- |
| 目的 | 验证客户端中途断开时服务端不会继续跑完并写缓存（否则「已无人接收的请求」会顶高在途，反过来触发降级） |
| 注入 | 发起一次流式排障请求后，在首帧后立即断开（Ctrl-C / 杀掉客户端进程） |
| 判据（≤5 分钟） | ① 服务端识别为 aborted 并停止后续生成；② 审计落一条 discontinued/delivered=false 的行；③ 在途读数回落；④ 不写缓存（或写缓存但标记）——事后能用审计证明"这次没有被记成成功" |
| 恢复 | 无需恢复；重复三次确认不是偶发 |
| 翻车面 | 断开只 `log.debug` 而包级日志是 INFO ⇒ 永不可见，等于没有这个信号 |

### 3.5 恢复旧库

| 段 | 内容 |
| --- | --- |
| 目的 | 验证唯一不可再生数据（账号库）**真的能恢复**，且恢复动作本身不制造第二个事故 |
| 注入 | **在演练库**上用备份包恢复：停服 → 恢复 → 起服 |
| 判据（≤5 分钟） | ① 恢复后能用备份时刻存在的账号登录；② **备份时刻之后被吊销/改密的账号不会复活**——必须显式处理 **token_ver 回退**（恢复后强制全员重新登录）；③ 恢复动作本身留审计（谁、何时、从哪个包）；④ 恢复耗时 ≤ RTO |
| 恢复/善后 | 演练库销毁；生产不动 |
| 硬约束 | 恢复**只允许在停止网关时做**（容器形态下 H2 锁跨挂载点不可靠，OPS §1 记过损坏事故）；备份包先 `unzip -t` + sha256 校验，校验不过不许恢复 |

### 3.6 发布回滚

| 段 | 内容 |
| --- | --- |
| 目的 | 验证「发布坏了能退回去」，而不是"重新打包再试一次"（Windows 上 JVM 锁着 jar 时会打出截断 jar） |
| 注入 | 隔离环境做一次正常发布 → 用一个已知坏制品/坏配置发布 → 触发回滚 |
| 判据（≤5 分钟） | ① 坏发布被识别（现网症状或门禁红），② 回滚动作有脚本、可重跑、幂等；③ 回滚后版本标识与审计里的版本一致；④ 在途请求在停服时不被截断（优雅停机）；⑤ 回滚总耗时 < RTO |
| 恢复 | 回到上一个已知好制品，确认抓取面与探针恢复 |
| 翻车面 | 版本号硬编码时，"回滚成功"可能是版本显示相同的两个不同制品——必须用 commit/build-info 判断，不能看版本号 |

## 5. 值班五分钟判据

### 5.1 什么叫"过了"

被叫醒后 **5 分钟内必须产出三件事**，缺一件即本次值班判**失败**（记失败复盘，不追责个人）：

1. **哪一层**：入口（网关）/ 状态层（Redis、账号库）/ 上游（模型、向量、检索）/ 客户端，四选一，并给出一条判据（不是猜）；
2. **谁受影响**：全部 / 单租户 / 单账号 / 只有新请求；
3. **下一步动作**：止损动作（给出具体命令或操作）或升级（给谁、为什么）。

**5 分钟拿不到结论也是结论**：立即按「监控面失效」处理——不要继续在监控里找答案，直接人工验证业务面
（发一次排障请求看是否还答得出来）。2026-10-22 实测的正是这种局面：抓取目标已 down 两小时，
面板全绿、告警为空。**监控不响 ≠ 系统没事**；此时唯一可信的信号是业务面本身。

### 5.2 三个高频症状的定位表

| 症状 | 30 秒 | 2 分钟 | 5 分钟（必须给出结论） |
| --- | --- | --- | --- |
| **登录 500 / 401 风暴** | 看入口是否整体不可用（一次健康检查 + 一次登录） | 分层：健康检查是否含账号库；账号库是否被锁/损坏；Redis 是否可连（登录失败计数与配额都在它上面） | 判定是「账号库坏」「Redis 坏」还是「鉴权配置坏（密钥/时钟）」；给出止损动作（停写、恢复备份、换密钥）并说明影响面 |
| **网关不可达** | 进程/端口/容器三处状态 | 谁死了：网关、中间件、还是网络；最近一次备份成功时间（判断能否重建） | 判定是「进程问题（起不来/被杀）」还是「依赖问题（起不来是因为连不上中间件）」；给出重启顺序（中间件 → 网关 → 桥/看门狗） |
| **降级常亮** | 读降级档位与最近一次切档事件 | 切档原因：在途超阈（负载）还是连续上游失败（模型故障）；上游 429 计数 | 判定「真实过载」还是「误判」（例：单用户打高并发 / 上游故障被计成熔断）；给出动作：限流单个来源 / 放宽或修复上游 / 人工清档并记录理由 |
